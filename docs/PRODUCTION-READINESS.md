# Before using real funds

The [public Devnet beta](https://www.uat.hiperia.xyz/) uses an isolated ORAO VRF program. Its October 31 deployed-byte verification, funded pool, actual purchases and fulfilled random draw are recorded in [the UAT review](./UAT-AUDIT.md#public-devnet-live-verification-october-31-2026). The November 1 user instruction also authorizes this public faucet-SOL game on the [production hostname](https://www.hiperia.xyz/), preserving old tickets and source-routed claims. Production uses the explicit `testnet-demo` plus `vrf` profile and the exact Devnet endpoint; it no longer selects the legacy restricted game for new purchases. Project protection settings and the separate canonical UAT alias remain unchanged. These Devnet checks do not establish a reviewed Mainnet lottery or authorize real funds.

## Keep out of GitHub and frontend deployments

- Wallet/deployer/upgrade-authority private keys, seed phrases and keypair JSON files.
- Real environment files, RPC provider secrets, Airtable tokens, Vercel tokens, OIDC tokens and deployment-protection bypass credentials.
- Local signing backups, upload buffers, test receipts, logs, caches, tool downloads and generated contract build directories.

The repository's ignore rules and frontend upload allowlist exclude the current local keys, build output and environment files. `.gitignore` cannot remove a credential already committed: if that happens, revoke or rotate it, then address repository history. Do not paste credentials into an issue or chat to verify them.

Source code, public wallet addresses, the program ID, the IDL, tests, lockfiles and an environment-variable template with non-secret placeholders can be public. A smart contract must remain secure when its source and deployed bytes are known.

Variables prefixed with `VITE_` become browser configuration. They must not contain private credentials. Keep signing authority outside the frontend and use narrowly scoped server secrets for external APIs.

The October 29 check found no high-confidence private-key or GitHub-token matches in the 94 currently tracked files. Repository history does contain four old local-validator keypair files under `test-ledger/`. Their public keys do not match the current Devnet deployer. Treat those historical test keys as exposed and never reuse them for a real wallet. This check does not prove that every possible credential format or external repository copy is clean; no history rewrite or credential rotation was performed.

## Protocol and operational requirements

1. Independently review the new verifiable-randomness integration and extend the recorded Devnet checks before a real-fund release. It binds one fresh request to a closed draw and uses rejection sampling for all 420 ordered pairs. Exact deployed bytes and a real oracle fulfillment were verified, with rejection simulations for wrong proofs and rerolls. A positive winning payout on the new VRF program has not yet been observed live; legacy payout evidence is separate. Native Rust/local-validator fixtures remain unrun in this Windows environment. Retain checks of oracle owner/address/seed/client, pre-existing-request rejection and absence of a predictable fallback, and retain the legacy ledger rather than migrating accepted tickets into new rules.
2. Preserve purchase-time price/prize snapshots, ownership checks and duplicate-claim protection. The November 5 v4 bankroll model removes full-prize admission checks for new daily and quick tickets while keeping only actual entry-refund holds, funded by incoming entries. Before enabling purchases, verify the separate nine-byte `get_bankroll_rules` revision 1: daily/quick enabled, entry refunds protected, no prize reserved at purchase, funding required at claim, version 4 and ledger size 50. New admissions use only `buy_bankroll_ticket`; old v2/v3 purchase instructions reject new entries. Protect all previously accepted v2 full-prize and v3 combination reserves and route each claim/refund through its version-specific handler. A v4 winning claim can use only funds above vault rent, old protected prizes and other pending entry holds. Insufficient funding must reject atomically without partial payment or a settled marker; the unpaid winner remains claimable without expiry after refill. Draw finalization must not depend on returning funds to a requester, and losing-only cleanup must not depend on the owner's current wallet account type. Reclaim oracle funding only to its immutable original requester; keep winning payouts owner-directed. Bind a buyer's quoted price/configuration revision across signing and upgrades, and establish refunds and outage behavior before taking money.
3. Review upgrade authority, deployment reproducibility, governance, monitoring and emergency controls. Explorer links provide transparency; they do not remove operator upgrade power.
4. Budget real hosting, domain, RPC, randomness and maintenance costs. Faucet SOL makes Devnet SOL costs test-only; hosting/RPC/domain services can still incur real charges. The reveal requester pays oracle fees and rents separately from the prize pool. A new v4 purchase raises vault balance and protected entry holds by the same amount, preserving available operator capital at checkout; prizes are not reserved or paid out on purchase. This permits new entries without the earlier full-prize treasury cap, but the operator accepts a possible shortfall when several fixed prizes become due. Disclose this funding-wait risk before every new purchase; show unpaid wins under Win as `Waiting for treasury funding`, retain them without expiry and require a fresh explicit claim after top-up. No automatic retry, payout keeper or first-in-first-out guarantee is configured. Twenty SOL and a positive expected house margin do not guarantee immediate payments or profit; legacy fixed results have no random-draw house margin.
5. Review dependencies and complete an independent security audit before real funds. The current review documents remaining dependency findings and test limitations.

The public program keeps the same fixed offers: 0.00625 SOL for a 2 SOL scheduled prize and 0.0072 SOL for a 1 SOL quick prize. Scheduled offers apply only to exact four-hour slots. Quick draws remain available without a wallet allowlist. The app reads these values from chain metadata. Both v4 draw types use the 50-byte canonical ledger derived from `bankroll-draw`, `v1` and the draw timestamp; its creator pays the actual rent separately from the prize vault. A v4 ticket cannot use a historical full-prize release handler.

Due draws still need an approved oracle-request transaction, oracle fulfillment and a finalization transaction; winning payouts require once-only ticket settlement. The approved completion can include version-specific reconciliation and at most six actual losing-ticket releases, with at most eight application instructions and room for two wallet-added compute-budget instructions. Optional reconciliation/cleanup-read failure must leave valid finalization available. V4 reconciliation idempotently releases only that finalized draw's pending entry-refund holds, pays zero SOL and never marks a ticket paid. A winning v4 claim can reconcile if needed; permissionless losing-only cleanup remains independent of the owner's current account type. Historical v3 reconciliation still retains every outstanding winning prize, and historical v2 losses still need confirmed reserve release. The explicit one-shot `npm run program:process-vrf-due` operator command can reconcile v4 holds or historical v3 backing and process actual losses; its default run is read-only, and execution records transaction receipts. Ongoing bulk reveal actions deduplicate the source program and draw timestamp, quote actual oracle costs once per draw, require explicit approvals and preserve confirmed progress on failure without automatic resubmission. A web countdown cannot execute these operations. No persistent publisher or settlement keeper is configured.

Refills must reach the actual [public program prize vault, FiYD4tUhgAgNE7D7fpoUDNzRWfR48EKo4Y4BfL5ekpMp](https://explorer.solana.com/address/FiYD4tUhgAgNE7D7fpoUDNzRWfR48EKo4Y4BfL5ekpMp?cluster=devnet), after verifying its source program. The administrator's personal wallet and the Support Hiperia donation wallet are different accounts; funding either is not a vault refill. Old valid claims must remain usable when new bankroll metadata or liquidity reads fail. A frontend balance estimate cannot override the contract's atomic funding check or constitute a payment queue. Review this operator-dependent liquidity model before any separately authorized real-fund release.

The new program implements a 24-hour entry-refund path only for open or still-unfulfilled draws. Fulfilled or finalized results cannot use that timeout refund, and accepted winning claims have no expiry. Winning payments and entry refunds require the immutable original recipient to remain a System Program wallet. An owner that changes its account type can therefore retain an unresolved refund's reserve; an undrawn ticket cannot be declared a loss to clear it. Finalization and actual losing-only cleanup are independent of that owner account type. Review outage behavior, immutable recipients, once-only transitions and the treatment of oracle/account costs before taking real funds.

The legacy referral campaign remains on-chain, while the new public game hides it and does not enroll new campaign purchases. No airdrop or cash referral reward is promised. Reintroducing incentives requires a separate economic and abuse review.
