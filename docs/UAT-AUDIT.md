## Public Devnet one-shot operations

The [public-game processor](../hiperia_program/scripts/process-vrf-due.js) is an explicit one-shot CLI; no timer, unattended keeper, or background transaction sender is installed. Its default invocation is read-only:

```powershell
node hiperia_program/scripts/process-vrf-due.js --max-draws 3 --max-settlements 20
```

The dry run reads the exact Devnet genesis, verified public-game metadata, actual draw/oracle states, ticket snapshots, reserve capacity and current oracle fee/rent quotes. Execution requires `--execute` and an explicit `--wallet` path or `HIPERIA_OPERATOR_WALLET`; it never chooses a default local wallet. `--max-oracle-lamports` approves a combined funding budget for all newly requested draws in that run and defaults to zero. Review the live dry-run quotes before setting a nonzero budget. This budget covers the quoted oracle fee and request/client rents; ordinary transaction fees are separate. A changed quote stops the request before submission. The contract also caps the signed oracle fee; chain rent remains governed by the active Rent sysvar.

`--max-draws` (1–10), `--max-settlements` (1–100), `--batch-size` (1–6), `--max-transactions` (1–50), and `--wait-seconds` (0–90) bound the one-shot work. Existing pending requests are checked and finalized without generating a replacement seed or paying a second oracle request fee. Finalized wins are always skipped, without an expiry or prize reduction. Only actual finalized losses are eligible for receiver-independent reserve release, after fresh ticket reads. Open draws beyond the request deadline remain unresolved and are reported for entry refunds rather than fabricated as losses.

Each signed transaction's identity is persisted before submission. Confirmation uses HTTP status polling, with RPC write retries disabled. An unknown signature or interrupted receipt blocks further writes until an operator reviews its status and target account, then manually archives the receipt. The CLI does not silently resubmit the same signed transaction or generate a replacement transaction after an uncertain outcome. Focused JavaScript tests cover dry-run behavior, budget changes, draw/batch bounds, win preservation, error stopping, receipt ordering and non-Devnet rejection; these tests do not prove live oracle fulfillment.

The separate finalization and loss-release paths remove the account-type dependency for normal fulfilled draws. A residual timeout case remains: ticket entry refunds and positive winning payments require the immutable original address to remain a System Program wallet. If that owner changes its account type and the draw remains genuinely unresolved beyond the 24-hour request/refund threshold, its refund may fail and its reserve can remain occupied. An undrawn ticket cannot be treated as a loss to release capacity. Accepted winning reserves also remain intentionally reserved until a valid payout. Finite reserves, timely explicit reveal/cleanup and outage monitoring remain operational requirements; this CLI is not an always-available liquidity guarantee.

## Historical fixed-result rules

- A new ticket contains two different numbers from 02 to 22. Order matters: 02 → 22 differs from 22 → 02.
- Each ticket enters one exact date and time. The daily schedule is every four hours: 02/06/10/14/18/22 Manila time. Separate occurrences require separate tickets.
- Daily times use Asia/Manila, UTC+8. The page updates its countdown every second. A selected draw stays selected as it expires; checkout asks for a new selection instead of moving the ticket silently. The chain's clock decides whether a purchase is on time.
- Quick entry remains 0.0072 SOL for a 1 SOL prize. Scheduled entry is 0.00625 SOL for a 2 SOL prize; all amounts are test SOL. The quick test targets about sixty seconds after checkout and avoids exact scheduled timestamps.
- Revision 3 fixes newly recorded results at 02 → 22, including scheduled and quick draws. Existing blockchain records retain their original numbers.
- An approved tester or administrator records the result after the draw. The contract supplies the numbers; the transaction does not accept an arbitrary result.
- Viewing results is read-only. Recording results costs a network fee and account rent. Claims and losing reserve processing cost network fees. The manual Close ticket button is removed. UAT claims have no expiry after the draw.
- Every accepted UAT ticket reserves its entire potential prize. A losing ticket releases that reserve when processed. A winning ticket spends its reserve when paid to its owner. For example, a vault with approximately 1.1 SOL and a 1 SOL prize can back one outstanding ticket. Process due tickets or fund more capacity. Multiple entries for the same daily timestamp are allowed when their full prizes can be reserved.

## Revision 4 reserve liveness change

The owner-signature requirement on settlement lets a ticket owner refuse to close a losing ticket and leave its entire prize reserve locked indefinitely. Hiding the close button or waiting for that owner's next purchase does not solve this. An inexpensive purchase can lock a much larger prize, so a reserve-denial attack does not require a wealthy attacker.

Revision 4 makes settlement permissionless while retaining the immutable ticket owner as the only possible payout recipient. A third party can pay the network fee, release a published losing ticket's reserve, or send a published winning ticket's original snapshotted prize directly to its owner. The owner no longer needs to sign that settlement. The owner account must be a System Program wallet. Ticket/result PDAs, the exact draw association, the chain clock, once-only settlement, reserve coverage and checked arithmetic remain enforced. There is no winning-claim expiry, arbitrary-recipient transfer or reserve bypass. Readonly `get_rules` reports revision 4 so clients can distinguish deployed permissionless support from revision 3; prices, prizes and historical account layouts do not change.

This change makes an operator/publisher crank possible; it does not execute transactions by itself. Result publication and settlement still need a funded transaction sender. The UI must never automatically request a wallet signature on page load or refresh. The new native checks cover recipient substitution, duplicate and early settlement, missing or mismatched results, and preserving other tickets' reserves. The validator flow now uses an unrelated fee payer and checks that the owner receives the entire prize. The native/validator checks remain unavailable in this Windows environment. The deployed ELF, metadata and actual third-party settlement flow were verified on Devnet, as described below.

Pending tickets still reserve capacity before their draw, potentially for the existing 24-hour buying window. Permissionless settlement prevents indefinite withholding after publication; it does not prevent short-term capacity exhaustion. The current on-chain allowlist blocks outside wallets, while an approved tester can still spend the finite faucet reserve using the publicly known winning pair. A public real-fund release needs a separately reviewed exposure policy, verifiable randomness and a monitored result/settlement service. Wallet count limits do not defeat Sybil wallets. A future per-draw maximum liability across mutually exclusive winning pairs could improve capital efficiency, but must account for duplicate-pair exposure and every outstanding draw without reducing any accepted prize promise.

## Odds and payout assumptions

There are 21 × 20 = **420 ordered pairs** for distinct picks from 02–22. This game uses ordered pairs.

For a genuinely uniform, unpredictable draw:

| Offer     |       Entry | Prize | Expected prize cost | Theoretical player return |
| --------- | ----------: | ----: | ------------------: | ------------------------: |
| Quick     |  0.0072 SOL | 1 SOL |     0.002380952 SOL |                    33.07% |
| Scheduled | 0.00625 SOL | 2 SOL |     0.004761905 SOL |                    76.19% |

These calculations exclude ticket rent, result rent, network fees and operating expenses. They do not guarantee profit or exploit resistance. An exact 400× offer would leave only 4.76% gross margin before expenses; the selected scheduled offer is 320× with 23.81% expected gross margin. The previous timestamp randomizer and biased mapping were unsafe and are not used. See the [economics report](./DODOS-ECONOMICS.md) for assumptions and costs.

For the fixed UAT result, a 02 → 22 ticket has a known winning outcome once its new result is recorded. Random-odds margin calculations do not apply to this mode. The allowlist and prize reserves are deliberate UAT controls.

## Before a public real-fund launch

The separate public Devnet program now binds a fresh verifiable randomness request to a closed draw and implements uniform pair sampling and timeout rules. Its recorded Devnet verification does not complete the independent review needed for real funds. Review that integration, accepted-prize invariants, refunds, oracle outages, upgrade governance and the chosen payout model, and complete supported native/validator testing plus a new-program live winning claim. A full-prize reserve per ticket is conservative and limits capacity; changing it requires a separate liability design.

The administrator still holds the upgrade authority. Explorer links make records inspectable; they do not make the game immutable or eliminate operator trust. A public launch also needs a dedicated RPC, controlled upgrade governance, and an independent review. Solana's [RPC guidance](https://solana.com/docs/rpc) documents public endpoint rate limits, and the Solana Foundation's [verifiable randomness lesson](https://github.com/solana-foundation/developer-content/blob/main/content/courses/connecting-to-offchain-data/verifiable-randomness-functions.md) explains why public on-chain inputs do not provide secure randomness.

## Dependency review

A bounded lockfile update patched `bn.js`, `shell-quote` and the existing major versions of `ws`. `npm audit --omit=dev` changed from 34 findings, including one critical and nine high, to **31 findings: zero critical, eight high, twenty-two moderate and one low**. This is not a clean dependency audit.

The critical `shell-quote` path came through the wallet adapter's React Native tooling peers; it was absent from the browser bundle and no shell-execution path was found in this app. The compatible update removes that reported issue. The direct runtime `bn.js` and server-installed `ws` packages also received compatible patches. See the [shell-quote advisory](https://github.com/advisories/GHSA-w7jw-789q-3m8p), [bn.js advisory](https://github.com/advisories/GHSA-378v-28hj-76wf) and [ws advisory](https://github.com/advisories/GHSA-96hv-2xvq-fx4p).

Remaining high findings include Anchor's Node-only `toml` workspace loader and React Native/tooling peers. Module inspection found those paths absent from the browser bundle; the RPC function imports Web3 utilities and uses HTTP, without an inbound WebSocket server or the Anchor workspace loader. This narrows observed exposure but does not prove those dependencies safe for other uses. Some fixes require incompatible major upgrades, so this change does not force them into the wallet/Anchor stack. Revisit them during the production dependency review.
